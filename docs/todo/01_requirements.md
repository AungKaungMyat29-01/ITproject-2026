# TODOアプリ 要件定義書（V1）

## 1. 目的と対象範囲

### 1.1 目的
既存のExpress＋TypeScript＋EJSサイトに、Neon（PostgreSQL）をデータベースとしたTODO管理機能を追加し、受講者がブラウザ（`/todo`）からFetch APIを介してTODOの一覧表示・登録・完了切替・削除を行えるようにする。

### 1.2 対象者と利用データ・セキュリティ
- **対象者**: 授業の受講生および講師（V1では認証機能を持たないため、公開URLでは第三者も閲覧・変更・削除が可能となる）
- **利用データ**: 架空の授業用データのみを使用し、個人情報や重要な情報は一切登録しない。
- **機密情報の管理**: 接続文字列や `.env` はGitに追加せず、AIにも渡さない。

### 1.3 実装・公開環境
- **バックエンド / テンプレート**: Express ＋ TypeScript ＋ EJS（既存のDB接続処理〔例：`db.ts`、実際の配置は要確認〕と環境変数 `DATABASE_URL` を利用[cite: 1.2]）
- **データベース**: Neon（PostgreSQL）※各学生が用意したNeon DBをPreviewとProductionで共通利用する[cite: 1.2]
- **ホスティング**: Vercel（Local、Vercel Preview、Productionの3環境で動作確認し結果を記録する[cite: 1.2]）
- **ルーティング方針**: 既存のトップページ `/` とDB接続確認 `/api/db-check` を残したまま、画面 `/todo` とAPI `/api/v1/todos` を追加する（実際のファイル配置の詳細は設計書で確定する[cite: 1.2]）。

### 1.4 対象外（V1で作らないもの）
- ユーザー認証・ログイン機能[cite: 1.2]
- タスクの優先度設定[cite: 1.2]
- タスクの絞り込み（フィルタリング）[cite: 1.2]
- 登録済みタスクのタイトル更新[cite: 1.2]

## 2. 機能要件と受け入れ条件

画面（`/todo`）からブラウザの `Fetch` を用いて REST API（`/api/v1/todos`）を操作する。（`TodoApi` クラスへの分割は設計書で扱う）

### REQ-01: TODO一覧取得
- **操作**: 登録済みのTODOを `id` の昇順（小さい順）に取得し、画面に表示する[cite: 1.2]。
- **入力**: なし（`GET /api/v1/todos`）[cite: 1.2]
- **結果**: ステータス `200` でTODOの配列を `data` に返す[cite: 1.2]。0件の場合は `200` で `data: []` を返す[cite: 1.2]。
- **エラー**: DB接続不可やサーバー内部異常時は `500` または `503` を返す。
- **受け入れ条件**:
  - 1件以上あるときは `id` 昇順で一覧表示されること[cite: 1.2]。
  - 0件なら `200` で `data` は `[]` となり、`/todo` 画面に「TODOがありません」と表示されること（初回の空DBまたは隔離環境で確認）[cite: 1.2]。
- **確認方法**: ブラウザで `/todo` を開き、0件時のメッセージ表示と複数件登録時の `id` 昇順表示、および `200` 応答を確認する[cite: 1.2]。

### REQ-02: TODO登録
- **操作**: 画面からタイトルを入力して送信し、アプリ側で前後の空白を除いて1〜100文字であることを確認してからDBへ保存する（`isCompleted` は `false` で開始）[cite: 1.2]。
- **入力**: `POST /api/v1/todos`、リクエスト本文 `{"title": "課題を提出する"}`[cite: 1.2]
- **結果**: ステータス `201` で採番済みのTODOを `data` に返す[cite: 1.2]。
- **エラー**:
  - `title` の欠落、型違い、JSONの構文エラー：`400 BAD_REQUEST`[cite: 1.2]
  - `title` が空白だけ、または101文字以上：`422 VALIDATION_ERROR`[cite: 1.2]
  - DB異常・内部エラー：`500` または `503`
- **受け入れ条件**:
  - 前後に空白を付けて登録しても、DBの保存値と応答の `title` は空白除去後の値になること[cite: 1.2]。
  - 不正入力時に適切なエラーコード（`400` または `422`）が返ること[cite: 1.2]。
- **確認方法**: 正常値（前後空白あり含む）・境界値（1文字、100文字）・異常値（空文字、空白のみ、101文字）で動作とステータスコードを確認する[cite: 1.2]。

### REQ-03: 完了状態の部分更新
- **操作**: 指定したTODOの完了状態（`isCompleted`）だけを更新する（V1では `title` を更新しない）[cite: 1.2]。
- **入力**: `PATCH /api/v1/todos/:id`（`:id` は1以上の整数）、リクエスト本文 `{"isCompleted": true}`（または `false`）[cite: 1.2]
- **結果**: ステータス `200` で更新後のTODOを `data` に返す[cite: 1.2]。
- **エラー**:
  - ID形式が不正、本文が空、`isCompleted` が真偽値でない：`400 BAD_REQUEST`[cite: 1.2]
  - 形式が正しく存在しないID：`404 NOT_FOUND`[cite: 1.2]
  - DB異常・内部エラー：`500` または `503`
- **受け入れ条件**:
  - 登録時に返されたIDを使うと、そのTODOだけの完了状態が変わり、リロード後も維持されること[cite: 1.2]。
  - 不正IDや存在しないIDに対して `400` / `404` が返ること[cite: 1.2]。
- **確認方法**: 画面から完了・未完了を切り替え、リロード後の状態維持と、存在しないID指定時の `404` 応答を確認する。

### REQ-04: TODO削除
- **操作**: 指定したTODOをDBから削除する[cite: 1.2]。
- **入力**: `DELETE /api/v1/todos/:id`（`:id` は1以上の整数）[cite: 1.2]
- **結果**: ステータス `204` を返し、レスポンス本文は返さない[cite: 1.2]。
- **エラー**:
  - ID形式が不正：`400 BAD_REQUEST`
  - 指定した `:id` が存在しない：`404 NOT_FOUND`
  - DB異常・内部エラー：`500` または `503`
- **受け入れ条件**:
  - 指定したIDのTODOが削除され、画面一覧から消えること。
  - `204` 応答時は本文がないため、フロントエンドでJSONとして解析せず正常終了すること。
- **確認方法**: 画面から削除を実行して一覧から消えること、および存在しないID指定時の `404` 応答を確認する。

## 3. 共通のデータ・エラー条件

### 3.1 データ制約とJSON形式
- **DBテーブル（`todo_tasks`）**: `id`（INTEGER・主キー・自動採番）、`title`（TEXT・必須・前後空白除去後1〜100文字）、`is_completed`（BOOLEAN・必須・初期値 `false`）、`created_at`（TIMESTAMPTZ・必須・初期値 `NOW()`）。
- **APIレスポンス変換**: DBの `is_completed`、`created_at` はJSONでは `{id, title, isCompleted, createdAt}` に変換する。
- **正常時JSON（GET / POST / PATCH）**: `{"status": "success", "data": ...}` とする（DELETE `204` は本文なし）。

### 3.2 エラー条件と共通フォーマット
エラー時は以下のJSON形式に統一し、SQLや接続文字列などの内部情報は返さない。
```json
{
  "status": "error",
  "code": "エラーコード",
  "message": "エラーメッセージ",
  "details": []
}
